<objective>
Fix the exclude-all collection leak (v1.0 milestone audit BLOCKER 1, affects CLI-04/CLI-05): when a user excludes every collection, search returns ALL documents instead of none. Root cause is a truthiness-vs-sentinel ambiguity: `src/sif/search/bm25.py:54` and `src/sif/search/vector.py:56` use `if options.collection_ids:`, so an empty list (exclude-all, emitted by the CLI when `repo.list_enabled()` returns nothing) is treated as "no filter". HybridSearcher and SearchPipeline delegate the same options object to both searchers, so fixing the two searchers fixes all paths.

Verified scope facts (planner, 2026-09-14):
- CLI sites (search.py x3, bench.py) already emit correct sentinels — `[]` when exclude-all or when no `-c` name matches; `None` when `--all`/search_all bypasses. NO CLI changes needed.
- MCP backend never passes `[]` (returns early on unmatched names), so the searcher guard leaves MCP behavior identical. Do NOT touch mcp/ (separate audit finding MCP-02).
- `src/sif/database/repository.py` search_fts/search_vector have no callers in src (searchers do raw SQL) — out of scope.
- `src/sif/core/context.py:153` builds context strings, does not filter results — out of scope.

Purpose: excluding all collections is an explicit user intent to see nothing; returning everything is an information-disclosure-grade semantic inversion live-reproduced by the audit checker.
Output: two searchers honor `[] = exclude everything, None = unfiltered`; regression tests lock the contract across bm25/vector/hybrid.
</objective>
