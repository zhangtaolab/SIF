The three behaviours and the mutant each test rejects:
1. A document-level row of a per-chunk page has no `Sequence` line in Markdown and no `sequence` element in XML, while chunk rows do (plan 19-10 truth 5 and Task 2 acceptance criterion 2). The audit showed that with both formatter conditions widened, 565 tests still passed. The new test renders the five-row page that holds the document-level row and fails on that mutant with a `Sequence` line where the Collection line belongs.
2. A path containing Rich markup renders literally in the per-chunk Chunk cell, which is the mitigation of threat T-19-24: the cell yields a plain `Text`, so no markup in a path is parsed. The audit found that the cell could yield a plain string or `Text.from_markup` without any test failing. The new test uses two paths Rich does parse and fails under both mutants.
3. `BM25Searcher.search_chunks` uses the displayed-score map of plan 19-12. Its only score test fed -1.0, where the earlier reciprocal map and the current one agree. The new test runs the method on a real FTS5 chunk index with raw values far from -1 and fails when the conversion goes back to the reciprocal map.

About the example name. The orchestrator's brief suggested a file named `r[3]eview-notes (v2).md`, which the UAT session had probed. Rich reads a bracketed tag only when it starts with a letter, a number sign, a slash or an at sign, so that name is not markup: the planner rendered it in a cell that parses markup and it still came out literal, so a test built on it would pass on the mutant. The test uses `/notes/[red]evil[/red].md`, which a markup-parsing cell renders without its tags, and `/notes/[/3]-review.md`, whose closing tag matches nothing and makes such a cell fail. The orchestrator agreed with this on 2026-11-26 and corrects the UAT record; this plan writes nothing into it.
