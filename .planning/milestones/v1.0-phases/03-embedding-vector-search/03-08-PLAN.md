<objective>
Close the single Phase 03 UAT gap G-03-3 (severity major, 03-UAT.md test 3): repeated `sif index embed` runs
pollute the vector store. embed_cmd calls chunk_repo.delete_by_document(doc.id) — deleting only
document_chunks rows — then re-chunks with fresh UUIDs (DocumentChunk.id defaults to uuid4) and calls
VectorSearcher.add_embeddings_batch, which is insert-only. The old document_embeddings rows for the deleted
chunk_ids are never removed, remain searchable through the denormalized vec0 metadata, and accumulate on
every run: the UAT observed 7 embed runs on a 3-chunk collection produce 21 document_embeddings rows with
21 distinct chunk_ids against 3 live document_chunks rows, and vsearch returning the same document 7 times
at identical score. The --force flag is accepted but ignored (the force parameter carries an unused-argument
suppression comment), so every run re-chunks everything.

This plan delivers the two missing items from the gap diagnosis: (1) a delete path for a document's
embeddings in VectorSearcher, wired into embed_cmd as delete-before-insert so re-chunked documents replace
their vectors; (2) honored --force semantics — the default run embeds only documents whose chunks lack a
complete, exact matching set of embeddings, --force re-embeds everything. Tests reproduce the UAT evidence
inverted against a real sqlite-vec database.

Purpose: make the D-10 batch embedding flow idempotent and crash-safe, so vector search results are
trustworthy after any number of embed runs (VEC-02 store integrity, VEC-03 embed flow).
Output: a tested delete/upsert-free replace path and --force semantics; the full quality suite green.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI invocation → embed_cmd | the --force flag and --collection name cross from user input into the indexing flow (existing surface, unchanged shape) |
| embed_cmd → local SQLite vector store | the new DELETE statements write to the vec0 virtual table holding the user's index data |

No new network egress, no new dependencies, and no new secret handling are introduced by this plan — it operates entirely on the local store through existing, parameterized SQL.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-08-01 | Tampering | document_embeddings integrity (orphaned vec0 rows polluting search results — the gap itself) | medium | mitigate | Delete-before-insert in the same transaction as the re-chunk (Task 1), plus the exact chunk-id-set completeness check (Task 2) that re-embeds any document whose stored vectors drift from its live chunks |
| T-03-08-02 | Tampering | delete_embeddings_by_document SQL construction | low | mitigate | Both new statements are fully parameterized (single ? placeholder per document id); no identifier or value is ever interpolated into SQL text — asserted by the unit test that inspects the executed SQL |
| T-03-08-03 | Denial of Service | repeated `sif index embed` runs re-embedding every chunk on remote openai backends (cost and traffic amplification per run) | low | mitigate | Default run skips fully embedded documents with zero embedding calls (Task 2 behavior 4); re-embedding is opt-in via --force |
| T-03-08-04 | Tampering | concurrent SIF processes embedding the same database | low | accept | SQLite writer locking serializes the transactions; each run replaces a document's vector set exactly, so concurrent runs converge to a consistent per-document state rather than accumulating orphans — the pre-fix append-only behavior was the actual corruption vector, and it is removed |
</threat_model>
