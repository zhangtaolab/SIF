<objective>
Close Phase 10 review finding CR-01 (critical, open): legacy direct-DELETE FTS5 sync triggers are never migrated, so pre-existing databases keep deleted content searchable indefinitely.

Decision recorded from RESEARCH.md Open Question 1 (no interactive user check in this chained run): adopt the detection-gated 'rebuild' — when a legacy direct-DELETE trigger is detected for either FTS table, run `INSERT INTO {fts_table}({fts_table}) VALUES('rebuild')` for that table in the same create_all() pass. Rationale: the audit's phrasing ("keep deleted content searchable") reads as wanting the state fixed, not just the mechanism; the file already has a rebuild-on-misconfiguration precedent (needs_rebuild_docs drop + reseed); external-content rebuild re-derives the index from the content tables so it cannot lose data; fresh databases pay nothing. FTS state is derived state, so this decision is reversible (re-runnable re-derivation).

Purpose: users' existing databases stop returning deleted documents after one open, instead of after a manual reindex.
Output: generalized detector + migration + gated rebuild in schema.py; three regression tests extending TestFtsUpdateTrigger.
Spec-less probe fallback skipped: phase has no requirement IDs to probe (visible skip).
</objective>
