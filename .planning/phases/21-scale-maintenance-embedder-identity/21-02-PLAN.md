<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| vector writer -> shadow | Every embedding write/delete must update the shadow in the same transaction |
| legacy database -> backfill | Existing stored rows become the derived shadow once |
| search path -> shadow read | A false negative marks a healthy result stale; a false positive hides a lagging one |
| maintenance -> shadow | Reconcile scans are allowed; search scans are not |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-21-05 | Tampering | embedded_documents maintenance | high | mitigate | Shadow rows are written only inside the caller's vector transaction, every insert joins `documents`, and cleanup/vacuum reconcile from the two source tables (Tasks 1-2). |
| T-21-06 | Denial of Service | search-path staleness read | medium | mitigate | One display-gate probe plus indexed PK lookups replace the O(vectors) scan; Task 3 asserts no `document_embeddings` scan during marking. |
| T-21-07 | Information Disclosure | stale marker correctness | low | accept | A shadow that lags would mislabel staleness, but markers are advisory and a re-run of reconcile or re-embed self-heals; no data is disclosed. |
| T-21-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package install occurs in this phase; the legitimacy gate is a no-op. |

## Residual Risk

Raw-SQL test fixtures or third-party scripts that write vec0 rows directly bypass the shadow until a reconcile runs. Production writers are funneled through `VectorSearcher`; the fixture audit in Task 1 removes the known raw writers, and Task 2's reconcile is the repair path. Accepted as a test-only residual.
</threat_model>
