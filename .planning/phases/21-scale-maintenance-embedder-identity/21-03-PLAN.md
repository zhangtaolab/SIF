<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| contexts table -> cached map | Stored context rows are cached in-process across search requests |
| another process -> cache | Cross-process writes must invalidate through SQLite's data_version |
| sentinel connection -> filesystem | The cache opens a second connection to the same database file |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-21-08 | Tampering | cached context map freshness | high | mitigate | Invalidate on the repository write generation, on a sentinel `PRAGMA data_version` change, and on inode change; sample all three before building (Tasks 1-2). |
| T-21-09 | Denial of Service | sentinel connection lifecycle | medium | mitigate | One lazily opened sentinel per resolved path per process, closed by atexit/reset, never opened for `:memory:`; open failure bypasses the cache (Tasks 1-2). |
| T-21-10 | Information Disclosure | contexts cache across databases | low | accept | The key is the resolved main DB path; two databases can never share a map. Paths are local to the single-user process. |
| T-21-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package install occurs in this phase; the legitimacy gate is a no-op. |

## Residual Risk

`PRAGMA data_version` is database-wide, so any commit (chunk writes, query-log rows, embeddings) invalidates the context map. That is conservative and correct; at personal-KB context counts the rebuild is one small query. Accepted.
</threat_model>
