## Summary

Reviewed all 18 in-scope files at standard depth: the eight CLI command modules,
`main.py`, `schema.py`, `mcp/backend.py`, the `sif-get` skill, the generated CLI
reference, and the six test files. Cross-referenced `utils/paths.py`,
`database/database.py`, `database/connection.py`, `database/repositories.py`,
`cli/formatters.py`, `search/vector.py`, `search/benchmark.py`, and
`indexing/scanner.py` to trace call chains. The scoped test files all pass
(154 passed), ruff check/format are clean, and the phase's specific goals
(path canonicalization on lookups, XML control-character sanitization, FTS
trigger migration, Database lifecycle ownership) are correctly implemented and
well locked by tests.

The adversarial pass nevertheless found a crash class the phase did not cover:
**all Rich-rendered output interpolates dynamic text without `rich.markup.escape`**.
Two reachable crash vectors come from that root cause — the user's search query
in table titles, and document/context content in `get`/`multi-get`/`context list`
bodies — verified experimentally against the project's installed Rich
(`MarkupError: closing tag '[/x]' doesn't match any open tag`). Beyond that:
a byte/char truncation bug in `multi-get`, whole-run transaction rollback
semantics in `index update` that contradict the same file's per-collection
design comments, an accepted-and-documented `subpath` argument that is silently
ignored, a raw-traceback path for the vec0 dimension-mismatch error whose
remediation advice (`sif cleanup`) cannot actually fix the problem, and an
undeclared test dependency (`pytest-asyncio`) that breaks a clean dev install.

## Critical Issues

### CR-01: Raw user query interpolated into Rich markup — search commands crash on queries containing a stray closing tag

**File:** `src/sif/cli/commands/search.py:275` (also 302, 421, 646, 672-678)
**Issue:** The search query is interpolated unescaped into Rich markup contexts:
`Table(title=f'Search Results: "{query}"')` (line 275), the same title in
`vsearch_cmd` (line 421) and `query_cmd` (line 646), and the `--explain`
diagnostics `console.print(f"\n[dim]Query: {query}[/dim]")` (line 302; the
`query_cmd` explain block prints titles, not the query, but the title is
equally unescaped). Rich parses these strings as console markup, so a query
containing a stray closing tag (e.g. `sif search 'foo [/b] bar'` or a pasted
`[/section]` marker) raises `rich.errors.MarkupError`, which no handler
catches — the user gets a raw traceback and exit code 1. Verified
experimentally against the project venv's Rich: a `Table` title containing
`[/b]` raises `MarkupError`. Valid tag pairs (e.g. `[red]...[/red]`) are
silently swallowed, corrupting the displayed query. Note the file already
escapes the Snippet column (`escape(_display_snippet(r))`, line 290) — the
query/title side of the same output was missed.

**Fix:**
```python
from rich.markup import escape
from rich.text import Text

# Titles: render as pre-built Text, which is never markup-parsed
table = Table(title=Text(f'Search Results: "{query}"'))

# Or escape the interpolated value and keep the f-string:
console.print(f"\n[dim]Query: {escape(query)}[/dim]")
```
Apply to all three commands' table titles and the `search_cmd` explain block.

### CR-02: Document, file, and context content rendered as Rich markup — crash or silent corruption on markup-like content

**File:** `src/sif/cli/commands/get.py:86,122-124,219` (primary); `src/sif/cli/commands/context.py:232`; `src/sif/cli/commands/search.py:288,296,433,440,659,667`
**Issue:** Document content, disk-fallback file content, and stored context
text are printed via `console.print(content)` / added as Rich table cells
without `rich.markup.escape`. Rich parses table cells and print arguments as
console markup (verified experimentally: a `Table.add_row` cell containing
`[/bold]` raises `MarkupError`). Consequences, all reachable from ordinary
notes content (e.g. a markdown file documenting Rich/BBCode markup, an XML
snippet with `[/note]`, or `--line-numbers` table content in search output):

- `sif get <path>` / `sif get multi-get ...`: any document whose content
  contains a stray `[/tag]` raises `MarkupError` → raw traceback, exit 1
  (get.py:122-124, 219; the disk fallback at :86).
- `sif context list`: context `content` goes straight into a table cell
  (context.py:232) → same crash on user-written context text.
- Silent data corruption: `[bold]…[/bold]`, `[link=…]` sequences in content
  are consumed as styling instead of printed (verified: `'x [bold]hidden[/bold] y'`
  renders as `x hidden y`).
- The search/vsearch/query tables escape only the Snippet column; the Title
  column (`r.title[:_TITLE_MAX_LEN]`, line 288) and the Content column
  (line 296) are unescaped.

The skill `sif-get` steers an agent to pipe whole files through this command,
making the disk-fallback and content paths a routine consumer of arbitrary
file bytes.

**Fix:**
```python
from rich.markup import escape
from rich.text import Text

# get.py / multi-get content bodies:
console.print(Text(content))          # Text is never markup-parsed

# context.py table cell:
table.add_row(ctx_item.context_type, ctx_item.path, Text(content_text))

# search.py Content/Title columns:
row.append(Text(content))
row.append(Text(r.title[:_TITLE_MAX_LEN] + "..." if len(r.title) > _TITLE_MAX_LEN else r.title))
```

## Warnings

### WR-01: multi-get `--max-bytes` truncates by characters after measuring bytes — non-ASCII output exceeds the cap

**File:** `src/sif/cli/commands/get.py:212-213`
**Issue:** The guard measures bytes (`len(content.encode()) > max_bytes`) but
the truncation slices characters (`content[:max_bytes]`). For multi-byte
content (CJK, emoji), `content[:max_bytes]` yields up to `max_bytes` code
points — up to 3-4x the byte cap (a 5-byte-capped CJK doc can emit ~15 bytes),
so the documented "Max bytes per file" contract is violated for exactly the
non-ASCII corpora this project targets. The MCP backend already implements the
correct byte-accurate truncation (`_truncate_content`, backend.py:28-35); the
CLI copy diverges. The test (`test_max_bytes_truncation_and_line_numbers`)
only exercises ASCII, so it cannot catch this.

**Fix:** Reuse the backend's algorithm (extract it into a shared util):
```python
encoded = content.encode("utf-8")
if len(encoded) > max_bytes:
    suffix = "\n... [truncated]"
    content = encoded[: max_bytes - len(suffix.encode("utf-8"))].decode(
        "utf-8", errors="ignore"
    ) + suffix
```

### WR-02: `index update` wraps ALL collections in one connection context — a later pre-update failure silently rolls back every earlier collection's work

**File:** `src/sif/cli/commands/index.py:55,97-108`
**Issue:** The entire multi-collection update loop runs inside a single
`with db.connection:` block (line 55). Python's sqlite3 connection context
manager commits only at block exit and rolls back on exception, so when
collection N's pre-update command fails (ClickException raised at lines
98-108), all uncommitted work from collections 1..N-1 — documents added,
updated, removed, chunk purges — is rolled back with no indication. The
console has already shown "Updating collection: X … Found N files" progress
for the rolled-back collections. This directly contradicts the design
rationale documented in the same file for `embed_cmd` (lines 350-353, "One
transaction per collection (CR-02): a failed collection rolls back only its
own work, and successful collections keep theirs") — the two sibling commands
have opposite, undocumented transaction semantics.

**Fix:** Move the per-collection body under `with db.transaction():` (matching
`embed_cmd`), committing each collection before the next one's pre-update
command runs; or, if all-or-nothing is intentional, document it and say so in
the failure message ("no changes were applied to any collection").

### WR-03: `collection ls` accepts (and documents) a `subpath` argument that is silently ignored

**File:** `src/sif/cli/commands/collection.py:330-334`
**Issue:** `collection_ls` declares `@click.argument("subpath", required=False)`
and immediately suppresses it with `# noqa: ARG001`. The parameter does
nothing: `sif collection ls notes sub/dir` lists the entire collection,
ignoring the subpath. The generated reference documents the argument
(docs/cli-reference.md:192-197), and the sibling top-level `ls` command
implements the equivalent filter (ls.py:51-53), so users have every reason to
believe it works.

**Fix:** Implement the same filter used by `ls_cmd`, or remove the argument
(and regenerate the docs):
```python
if subpath:
    prefix = subpath.strip("/")
    files = [p for p in scan_result.files if str(p).strip("/").startswith(prefix)]
else:
    files = scan_result.files
```

### WR-04: vec0 dimension-mismatch `RuntimeError` escapes every CLI command as a raw traceback, and its remediation advice (`sif cleanup`) cannot fix the problem

**File:** `src/sif/database/schema.py:335-339`
**Issue:** `_create_vector_tables` raises a bare `RuntimeError` when
`SIF_EMBEDDING_DIM` disagrees with the stored `FLOAT[n]` declaration. Every
command calls `db.init_schema()` unguarded (e.g. index.py:53, 263-264;
search.py:198-199; get.py:53-54; main.py:121-122), so a user who changes the
dimension and runs any command — including `status` and `get` — gets a raw
`RuntimeError` traceback rather than a Click error. Additionally the message
advises "Rebuild the index with 'sif cleanup'", but `cleanup_cmd`
(main.py:147-199) only deletes orphaned rows; it never drops or recreates
`document_embeddings`, so the suggested remedy cannot change the dimension —
only deleting the database file works. Note `embed_cmd`'s friendly
dimension-mismatch ClickException (index.py:298-309) only fires for the
model-vs-table case; the settings-vs-table case raises inside `init_schema`
first, which is why the traceback path is the one users actually hit.

**Fix:** Wrap the mismatch in a Click-friendly error at the CLI boundary or
convert in `Database.init_schema`; and correct the message:
```python
raise RuntimeError(
    f"Embedding dimension mismatch: database has FLOAT[{existing_dim}], "
    f"but settings require FLOAT[{self.embedding_dim}]. "
    "Delete the database file and re-run 'sif index update' + 'sif index embed'."
)
```
(Consider `raise click.ClickException(...)` at the call sites, or catching
`RuntimeError` from `init_schema` in `main.py`'s shared path.)

### WR-05: bench fixture parse and validation errors surface as raw tracebacks

**File:** `src/sif/cli/commands/bench.py:68-69,125`
**Issue:** `json.load(f)` on a malformed fixture raises `JSONDecodeError` and
`SearchEvaluator(fixture_data)` raises `ValueError("Fixture must contain
'queries' key")` (benchmark.py:58-65) — both uncaught, producing tracebacks
for ordinary user input errors. The `try/except` that wraps evaluation
(lines 126-129) deliberately converts failures to `click.ClickException`, but
the fixture-load step it precedes was left out.

**Fix:**
```python
try:
    with open(fixture) as f:
        fixture_data = json.load(f)
    evaluator = SearchEvaluator(fixture_data)
except (json.JSONDecodeError, ValueError) as e:
    raise click.ClickException(f"Invalid fixture file {fixture}: {e}") from e
```

### WR-06: `pytest-asyncio` is used by in-scope tests but not declared in dev dependencies

**File:** `tests/unit/mcp/test_backend.py:25` (and every `@pytest.mark.asyncio` in the file)
**Issue:** The entire test module is annotated `@pytest.mark.asyncio`, which
requires the pytest-asyncio plugin. It is installed in the current venv
(1.4.0) but absent from `[project.optional-dependencies].dev`
(pyproject.toml:43-49, which lists only pytest, pytest-cov, black, ruff, ty).
A fresh `pip install -e ".[dev]"` (the install step documented in CLAUDE.md)
fails or silently skips all 10 async tests in this module, so CI or
contributors get a red/green result that depends on transitive environment
state.

**Fix:** Add `"pytest-asyncio>=0.23"` to the `dev` extra and pin the mode in
`pyproject.toml`:
```toml
[tool.pytest.ini_options]
asyncio_mode = "strict"
```

### WR-07: `vsearch_cmd` does not convert `VectorSearcher` construction failure into a Click error

**File:** `src/sif/cli/commands/search.py:400`
**Issue:** `VectorSearcher.__init__` raises `RuntimeError` when the sqlite-vec
extension is unavailable (vector.py:20-23). `embed_cmd` wraps construction in
`try/except RuntimeError -> ClickException` (index.py:345-348) and `query_cmd`
wraps `pipeline.search` the same way (search.py:595-598), but `vsearch_cmd`
calls `VectorSearcher(db.connection, len(query_embedding))` bare. When
sqlite-vec fails to load on the connection (broken install, platform
extension issue — `Database._enable_extensions` swallows the load error, so
the failure surfaces exactly here), the user gets a raw traceback.

**Fix:**
```python
try:
    searcher = VectorSearcher(db.connection, len(query_embedding))
except RuntimeError as e:
    raise click.ClickException(str(e)) from e
```

### IN-03: `index update` keys existing documents by raw path strings, unlike every other lookup fixed in this phase

**File:** `src/sif/cli/commands/index.py:121,137,148,188-197`
**Issue:** `existing_docs = {d.path: ...}` vs `scanned_paths.add(str(file_path))`
compares stored and scanned paths as raw strings. The scanner resolves paths,
and current rows are written from scanner output, so the common case matches —
but any hand-migrated or cross-machine row stored under a non-canonical
spelling (the DEBT-PN scenario this phase exists for) is invisible to the
`existing` lookup, gets deleted as "no longer exists", and is re-created with
a new UUID: full chunk/embedding purge and re-embed for that document, and a
changed document id. Sibling lookups (`get`, `multi-get`, MCP backend, prune)
all compare through `normalize_path`; this one does not.
**Fix:** Key both sides by `normalize_path(...)` (or state the invariant
"stored doc paths are always scanner-resolved" where it is relied upon).

### IN-04: `ls` subpath filter matches string prefixes without a path-component boundary

**File:** `src/sif/cli/commands/ls.py:52-53`
**Issue:** `d.path.strip("/").startswith(prefix)` means subpath `note` also
matches `notes2/x.md` and `notebook.md`. A component-boundary comparison
(`prefix == part or prefix + "/"` forms) would match user intent.
**Fix:** Compare on `Path(d.path).relative_to(...)` parts or append `"/"` when

### IN-08: `collection ls` tree build crashes on a non-canonical stored collection path

**File:** `src/sif/cli/commands/collection.py:366`
**Issue:** `file_path.relative_to(collection.path)` raises an uncaught
`ValueError` when the stored `collection.path` string differs from the
scanner's resolved form (hand-migrated row, or a path whose resolution changed
after a symlink moved). The scanner always resolves
(scanner.py `root_path = Path(root_path).resolve()`), so this needs a

here it is a traceback rather than churn.
**Fix:** Normalize both sides: `rel = file_path.relative_to(Path(collection.path).resolve())`
inside a try/except with a fallback to the full path string.

### IN-09: Impossible-state guard — `if not coll: continue` defends against list elements that cannot be None

**File:** `src/sif/cli/commands/index.py:80-81,327-328`; `src/sif/cli/commands/ls.py:47-48`
**Category:** necessity
**Issue:** Both loops guard against `None` collection objects. In the named
branch, `collections = [coll_repo.get_by_name(...)]` can hold `None`, but the
explicit `if not collections[0]: raise click.ClickException(...)` immediately
above (index.py:64-65, 318-319; ls.py:41-42) exits before the loop in that
case. In the `list_all()` branch, `CollectionRepository.list_all` maps every
row through `_row_to_collection`, which always returns a truthy `Collection`
(repositories.py:63-66, 113-131) — never `None`. So the guard evaluates on
every iteration but the state it defends against is unreachable from either
branch.
**Fix:** Drop the `if not coll: continue` lines (the explicit not-found raise
already covers the only None-producing path), or restructure to
`collections = [c for c in ... if c]` at assignment.
