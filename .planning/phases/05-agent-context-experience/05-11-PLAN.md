<objective>
Close review critical CR-01: escape every user-derived string crossing a Rich API in the three search commands' default table output (and their --explain prints), so markup-bearing queries, titles, collection names, and content render literally instead of crashing with `rich.errors.MarkupError` or silently swallowing bracket text.

Purpose: Rich parses console markup in `Table` titles and cell strings by default. The user's query is interpolated raw into the table title in all three commands (`Table(title=f'Search Results: "{query}"')` at search.py:275, vsearch :421, query :646). A query or indexed title containing an unmatched closing tag — e.g. `[/]` or `[/3]`, entirely plausible when searching notes about coding or markup — kills the command with a raw traceback (reproduced empirically by the reviewer and the phase verifier). Matched-but-unknown tags are silently swallowed instead: a title cell `todo [wip] note` renders as `todo  note`. Only the Snippet column is currently escaped (`escape(_display_snippet(r))` at :290 and :661 — the 04-06 fix applied to one column of five and to neither of the other two tables' cells). The verifier recommends folding this fix into the same round as gap 1; it is a display-layer fix only — the agent-facing `--json` path (which carries `context_description`, CTX-03) never passes through Rich and is unaffected.

Output: `escape()` applied to the query in all three table titles, to the truncated-title cell expression and `r.collection_name` in all three row builders, to the line-numbers content cell appends, and to the query/title in the two explain prints; five markup-literal regression tests in TestSearchOutputBranches reusing its `_invoke_bm25` / `_invoke_query` / `_invoke_vsearch` helpers.
</objective>
