<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PyPI index -> developer environment | Users install by name/version; confusion or a spoofed index would run untrusted code. |
| published artifact -> provenance verifier | Attestation verification binds the wheel to the repository identity. |
| tag -> immutable release | A mistake consumes a version permanently. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-17-23 | Tampering | published wheel bytes | high | mitigate | Build-once workflow guarded in plan 17-05; PEP 740 attestation verification against repository zhangtaolab/sif proves the published bytes came from the trusted workflow. |
| T-17-24 | Spoofing | install-resolution confusion | medium | mitigate | Install proofs pin `docsif==1.1.2` and use official indexes; TestPyPI install explicitly adds the PyPI extra index for dependencies; scratch venvs only. |
| T-17-25 | Repudiation | unattested or mislabeled release | medium | mitigate | PyPI JSON version + marker assertions and pypi-attestations verification must both pass; failure stops the phase. |
| T-17-26 | Denial of Service | immutable version consumed by a failed partial upload | medium | accept | PyPI immutability means a partial failure needs a new patch version; the plan documents the one-way decision instead of attempting an artifact mutation. |
| T-17-SC-07 | Tampering | npm/pip/cargo installs | high | mitigate | Test installs use official PyPI/TestPyPI indexes with a pinned version; `uvx pypi-attestations` is an ephemeral verification tool, not a project dependency; no package is added to the project. |
</threat_model>
