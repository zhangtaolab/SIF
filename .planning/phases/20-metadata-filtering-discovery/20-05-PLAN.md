It takes already-compiled fragments (the DB layer never imports the compiler); the caller compiles with `compile_filter(node, alias="d", scope="corpus")` and `compile_match(node, alias="mv")`. An absent filter or match is passed as `None`, never as the compiler's empty `("", [])` fragment: `filteredDocuments` is present exactly when a filter was supplied, and an empty fragment would falsely signal a supplied filter.

    Return the frozen envelope: `documents` (integer — eligible documents in scope, collection predicate only), `filteredDocuments` (integer, present only when `filter_predicate` is not None — scope AND filter), `totalKeys` (integer), `remainingKeys` (integer), `skippedKeys` (integer), `builtIns` (fixed two-entry list, described below), and `keys` (list). Each key entry is `{"key": str, "documents": int, "types": [...]}`; each type entry is `{"type": "string"|"number"|"boolean", "multiValued": bool, "documents": int, "distinctValues": int, "values": [{"value": ..., "documents": int}, ...], "remainingValues": int, "range": {"min": float, "median": float, "max": float} | absent}` — `range` only on the `number` type. These camelCase names are the deliberate mixed-casing contract (D-15); the dict is the wire shape, and the MCP pydantic models mirror it exactly.

    `builtIns` satisfies D-03. It holds exactly two entries in fixed order `path` then `mtime`, each shaped like a key summary (`{"key", "documents", "types": [...]}`) but computed from the `documents` columns over the same eligible region — never from `document_metadata_values`, and never listed inside `keys` or counted in `totalKeys`/`remainingKeys`. `path` has one string type; `mtime` has one number type carrying `range` (min/median/max over the region's `mtime` values). Built-ins do not enumerate values: `values` is `[]`, `remainingValues` equals `distinctValues`, and `distinctValues` is `COUNT(DISTINCT path)` / `COUNT(DISTINCT mtime)` over the region. `documents` for each built-in equals the region size (both columns are `NOT NULL`), so a supplied filter narrows it exactly as it narrows `filteredDocuments`. `match_predicate` narrows only the frontmatter `keys` list; the built-ins section is invariant across every discovery call so D-03 always holds.

    Region: one eligible-id CTE from `documents d` with the collection predicate and `filter_predicate`. Every frontmatter aggregate joins `document_metadata_values mv` to that region. `match_predicate` narrows the reported frontmatter entries (keys, types, values, distinct counts) but never the document denominators and never the `builtIns` section. Query budget: one query each for `documents`, `filteredDocuments` (when needed), `totalKeys`, the key window, `skippedKeys`; then at most two batched queries for the page's keys (type split with `COUNT(DISTINCT document_id)` and `MAX(ordinal) > 0`, and a values `GROUP BY key, value_type, text_value, number_value, boolean_value` with `HAVING COUNT(DISTINCT document_id) >= ?`), plus one median query for the numeric keys, plus two fixed built-in queries (`path` counts; `mtime` counts/min/max and its median window) that do not depend on the key window. Aggregate only the page's keys — never materialize the whole value space.

    Ordering: `sort="count"` orders keys `documents DESC, key ASC`; `sort="value"` orders `key ASC`. Values order `documents DESC`, then a stable string form of the value ascending. `min_count` filters value entries (and their counts) before windowing, so `distinctValues` is the post-`min_count` count and `remainingValues = max(0, distinctValues - len(values))`. `remainingKeys = max(0, totalKeys - len(keys))`.

    Median: `ROW_NUMBER() OVER (PARTITION BY key ORDER BY number_value)` and `COUNT(*) OVER (PARTITION BY key)` filtered to `position IN ((total + 1) / 2, (total + 2) / 2)`, then average the one or two rows in Python with `/ 2.0`. Integer division is load-bearing; do not replace it with `AVG`.

    `skippedKeys` counts `document_metadata_skips` rows joined to the eligible region; only documents in scope count.
